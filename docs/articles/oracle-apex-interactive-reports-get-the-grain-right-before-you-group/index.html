التقارير التفاعلية في Oracle APEX: اضبط مستوى الصف قبل التجميع

بقلم كريم الجيزاويEN / العربية6 دقائق قراءة

English version

An Interactive Report can answer several business questions without becoming several separate pages. My original LinkedIn post compared Control Break, Group By, and Pivot. The important starting point comes before choosing any of them: what does one source row represent?

Here is a small, reproducible reporting exercise. It includes expected totals and a join trap that can produce a convincing but incorrect summary. All names and amounts are synthetic; the queries read constants from DUAL and change no business data.

Start with one row per invoice

In a development application, create an Interactive Report region with this SQL source:

WITH invoices(invoice_id, branch, invoice_date, sales, cost) AS (
    SELECT 1001, 'North', DATE '2026-01-05', 120, 80 FROM dual UNION ALL
    SELECT 1002, 'North', DATE '2026-01-15',  80, 60 FROM dual UNION ALL
    SELECT 1003, 'South', DATE '2026-01-20', 150,110 FROM dual UNION ALL
    SELECT 1004, 'North', DATE '2026-02-05', 100, 70 FROM dual UNION ALL
    SELECT 1005, 'South', DATE '2026-02-12', 130, 90 FROM dual UNION ALL
    SELECT 1006, 'South', DATE '2026-02-20',  70, 40 FROM dual
)
SELECT invoice_id,
       branch,
       invoice_date,
       TO_CHAR(invoice_date, 'YYYY-MM') AS month_label,
       sales,
       cost,
       sales - cost AS margin
FROM invoices

The six source rows represent six complete invoices. MARGIN is an amount, not a percentage. All amounts use one assumed currency and all costs are known. A real report needs explicit rules for currency conversion, returns, and missing costs before its totals are meaningful.

Leave numeric columns numeric and apply display formatting in column attributes. Use MONTH_LABEL for the demonstration's month selection. Including the year avoids combining January from different years. Oracle: report column attributes

In the region's Actions Menu attributes, enable Control Break, Aggregate, Group By, Pivot, Filter, and Save Report as appropriate. Developers control which capabilities are available. Oracle: Actions menu configuration

Choose the view that matches the question

Control Break answers: which invoices belong to each branch? Enable a break on BRANCH, keeping the detailed invoice rows. Add Sum aggregates on SALES, COST, and MARGIN. You should still be able to inspect the six invoices beneath their branch headings. Oracle: Control Break

Group By answers: how much did each branch contribute? Select BRANCH as the grouping column, Sum for the three amounts, and Count on the non-null INVOICE_ID. The expected summary is:

Branch Invoice count Sales Cost Margin
North 3 300 210 90
South 3 350 240 110

Here the count means invoices because the source grain is one invoice. That interpretation would change if the query returned invoice lines. Oracle: Group By

Pivot answers: how do branch sales compare across months? Set the row column to BRANCH, the pivot column to MONTH_LABEL, and the function to Sum of SALES. Expected cells are:

Branch 2026-01 2026-02
North 200 100
South 150 200

Pivot changes the arrangement used for comparison; it cannot repair duplicated source amounts. Oracle: Pivot reports

These user-guide workflows reference 26.1; the developer settings reference 26.2. The 26.2 report experience was refreshed, so use the named operations and check the layout in your deployed version. Oracle: 26.2 report changes

Reconcile after changing filters

Without filters, the six invoices total sales 650, cost 450, and margin 200. Filtering MONTH_LABEL to 2026-02 should leave three invoices, sales 300, cost 200, and margin 100. Switching between details, grouping, and pivot should preserve the intended filtered population.

Save a private view named “February branch review” if that option is available to your authenticated user. Treat it as a saved report definition, not a historical copy of the underlying records. Clear or reset the filter deliberately before checking the all-month totals again. A hidden filter can make two otherwise-correct summaries appear inconsistent.

A join can break every view at once

This separate example contains two invoices worth 100 each. The first invoice has two lines. Predict the totals before running the read-only query:

WITH invoices(invoice_id, invoice_total) AS (
    SELECT 1, 100 FROM dual UNION ALL
    SELECT 2, 100 FROM dual
), invoice_lines(invoice_id, line_id) AS (
    SELECT 1, 11 FROM dual UNION ALL
    SELECT 1, 12 FROM dual UNION ALL
    SELECT 2, 21 FROM dual
)
SELECT SUM(i.invoice_total) AS repeated_total,
       SUM(DISTINCT i.invoice_total) AS distinct_amount_total,
       COUNT(DISTINCT i.invoice_id) AS invoice_count
FROM invoices i
JOIN invoice_lines l ON l.invoice_id = i.invoice_id

Expected output is REPEATED_TOTAL = 300, DISTINCT_AMOUNT_TOTAL = 100, and INVOICE_COUNT = 2. The correct invoice total is 200.

The join repeats the first header amount. SUM(DISTINCT invoice_total) also fails: it removes equal amounts, not duplicate invoice identities. A distinct invoice count can be correct while the monetary sum is wrong. Oracle documents that aggregate DISTINCT operates on distinct argument values. Oracle: aggregate semantics

Keep invoice-level amounts at invoice grain. If lines are needed only to select eligible invoices, consider an EXISTS filter; if line measures are needed, aggregate them to the required grain before joining. Then reconcile keys and amounts against a known population.

Use a new page when the underlying question, authorization, or data contract actually differs. For alternate analytical presentations of the same permitted rows, start by making the source grain reliable, then choose the reporting view. The SQL results above are expected values checked by arithmetic, not a claim of execution in your APEX application.

النسخة العربية

التقرير التفاعلي يقدر يجاوب على أكثر من سؤال عمل بدون ما يتحوّل لصفحات منفصلة. البوست الأصلي على LinkedIn قارن بين Control Break وGroup By وPivot. لكن البداية المهمة تسبق اختيار أي واحدة منها: الصف الواحد في مصدر البيانات يمثّل إيه؟

دي تجربة تقارير صغيرة قابلة لإعادة البناء، فيها إجماليات متوقعة وفخ في الربط ممكن ينتج ملخصًا مقنعًا لكنه غلط. الأسماء والمبالغ كلها افتراضية؛ الاستعلامات تقرأ ثوابت من DUAL ولا تغيّر بيانات العمل.

ابدأ بصف واحد لكل فاتورة

داخل تطبيق تطوير، أنشئ Interactive Report region بالاستعلام التالي كمصدر SQL:

WITH invoices(invoice_id, branch, invoice_date, sales, cost) AS (
    SELECT 1001, 'North', DATE '2026-01-05', 120, 80 FROM dual UNION ALL
    SELECT 1002, 'North', DATE '2026-01-15',  80, 60 FROM dual UNION ALL
    SELECT 1003, 'South', DATE '2026-01-20', 150,110 FROM dual UNION ALL
    SELECT 1004, 'North', DATE '2026-02-05', 100, 70 FROM dual UNION ALL
    SELECT 1005, 'South', DATE '2026-02-12', 130, 90 FROM dual UNION ALL
    SELECT 1006, 'South', DATE '2026-02-20',  70, 40 FROM dual
)
SELECT invoice_id,
       branch,
       invoice_date,
       TO_CHAR(invoice_date, 'YYYY-MM') AS month_label,
       sales,
       cost,
       sales - cost AS margin
FROM invoices

صفوف المصدر الستة تمثّل ست فواتير كاملة. MARGIN مبلغ، وليس نسبة مئوية. نفترض عملة واحدة وكل التكاليف معروفة. التقرير الحقيقي يحتاج قواعد صريحة لتحويل العملات والمرتجعات والتكاليف المفقودة قبل أن تكون إجمالياته ذات معنى.

احتفظ بالأعمدة الرقمية كأرقام، وطبّق تنسيق العرض من خصائص الأعمدة. استخدم MONTH_LABEL لاختيار الشهر في التجربة. وجود السنة يمنع جمع يناير من سنوات مختلفة مع بعضه. Oracle: خصائص أعمدة التقرير

في خصائص Actions Menu للمنطقة، فعّل Control Break وAggregate وGroup By وPivot وFilter وSave Report حسب الحاجة. المطور يتحكم في الإمكانيات المتاحة. Oracle: إعداد قائمة Actions

اختَر العرض المناسب للسؤال

Control Break تجيب: أي فواتير تخص كل فرع؟ فعّل التجميع البصري على BRANCH مع الاحتفاظ بصفوف الفواتير التفصيلية. أضف Sum في Aggregate لأعمدة SALES وCOST وMARGIN. المفروض تظل قادرًا على مراجعة الفواتير الست تحت عناوين الفروع. Oracle: Control Break

Group By تجيب: كل فرع ساهم بكام؟ اختَر BRANCH كعمود التجميع، وSum للمبالغ الثلاثة، وCount على INVOICE_ID غير الفارغ. الملخص المتوقع:

الفرع عدد الفواتير المبيعات التكلفة الهامش
North 3 300 210 90
South 3 350 240 110

العدد هنا يعني فواتير لأن صف المصدر يمثّل فاتورة واحدة. المعنى يتغيّر لو الاستعلام يرجع بنود الفاتورة. Oracle: Group By

Pivot تجيب: مبيعات الفروع تتقارن إزاي عبر الشهور؟ اختَر BRANCH لصفوف المقارنة، وMONTH_LABEL لعمود الـPivot، والدالة Sum على SALES. الخلايا المتوقعة:

الفرع 2026-01 2026-02
North 200 100
South 150 200

الـPivot تغيّر ترتيب العرض للمقارنة، لكنها لا تصلح مبالغ مكررة في المصدر. Oracle: تقارير Pivot

خطوات دليل المستخدم المشار إليه تخص 26.1، وإعدادات المطور تخص 26.2. تجربة التقارير اتحدثت في 26.2، فاستخدم أسماء العمليات وراجع ترتيب الواجهة في إصدارك. Oracle: تغييرات تقارير 26.2

طابق الإجماليات بعد تغيير الفلاتر

بدون فلاتر، الفواتير الست مجموعها مبيعات 650 وتكلفة 450 وهامش 200. فلترة MONTH_LABEL على 2026-02 المفروض تترك ثلاث فواتير، بمبيعات 300 وتكلفة 200 وهامش 100. التنقل بين التفاصيل والتجميع والـPivot لازم يحافظ على مجموعة البيانات المفلترة المقصودة.

احفظ عرضًا خاصًا باسم «مراجعة الفروع في فبراير» لو الخيار متاح للمستخدم المسجل. اعتبره تعريف تقرير محفوظًا، وليس نسخة تاريخية من السجلات نفسها. امسح أو أعد ضبط الفلتر بشكل مقصود قبل مراجعة إجماليات كل الشهور. فلتر غير ملحوظ ممكن يجعل ملخصين صحيحين يبدوان متعارضين.

الربط ممكن يفسد كل العروض مرة واحدة

المثال المنفصل ده فيه فاتورتان، كل واحدة بقيمة 100، والفاتورة الأولى لها بندان. توقّع الإجماليات قبل تشغيل الاستعلام الذي يقرأ فقط:

WITH invoices(invoice_id, invoice_total) AS (
    SELECT 1, 100 FROM dual UNION ALL
    SELECT 2, 100 FROM dual
), invoice_lines(invoice_id, line_id) AS (
    SELECT 1, 11 FROM dual UNION ALL
    SELECT 1, 12 FROM dual UNION ALL
    SELECT 2, 21 FROM dual
)
SELECT SUM(i.invoice_total) AS repeated_total,
       SUM(DISTINCT i.invoice_total) AS distinct_amount_total,
       COUNT(DISTINCT i.invoice_id) AS invoice_count
FROM invoices i
JOIN invoice_lines l ON l.invoice_id = i.invoice_id

الناتج المتوقع هو REPEATED_TOTAL = 300 وDISTINCT_AMOUNT_TOTAL = 100 وINVOICE_COUNT = 2. إجمالي الفواتير الصحيح 200.

الربط يكرّر مبلغ رأس الفاتورة الأولى. واستخدام SUM(DISTINCT invoice_total) يفشل أيضًا: يزيل المبالغ المتساوية، وليس تكرار هوية الفاتورة. ممكن عدد الفواتير المختلفة يكون صحيحًا بينما مجموع الأموال غلط. توثّق Oracle إن DISTINCT داخل التجميع يعمل على القيم المختلفة للمعامل. Oracle: قواعد التجميع

احتفظ بمبالغ الفواتير على مستوى الفاتورة. لو البنود مطلوبة فقط لاختيار الفواتير المؤهلة، فكّر في فلتر EXISTS. ولو محتاج مقاييس البنود، جمّعها للمستوى المطلوب قبل الربط. بعد كده طابق المفاتيح والمبالغ مع مجموعة بيانات معروفة.

أنشئ صفحة جديدة عندما يختلف سؤال العمل أو الصلاحيات أو عقد البيانات فعلًا. أما طرق التحليل المختلفة لنفس الصفوف المسموح بها، فابدأ بصحة مستوى المصدر ثم اختَر عرض التقرير. نواتج SQL المذكورة قيم متوقعة راجعنا حساباتها، وليست ادعاء بتنفيذها داخل تطبيق APEX الخاص بك.
