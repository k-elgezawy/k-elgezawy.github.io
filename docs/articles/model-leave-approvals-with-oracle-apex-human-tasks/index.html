تنظيم موافقات الإجازات باستخدام Human Tasks في Oracle APEX

English version

My original LinkedIn post used a leave request to explain approval tasks in Oracle APEX. A useful starting point is to separate three things: the request record, the human decision, and the process that connects several steps.

A Task Definition describes a reusable human task. Each submitted request can create its own task instance. A broader workflow can coordinate additional activities; a single approval does not require you to design a whole workflow first.

Define the decision and its participants

In Shared Components, open Task Definitions under Workflows and Automations. For a development example, create an Approval Task with static ID LEAVE_APPROVAL. An Action Task suits work that needs completion without an approval outcome. Configure a task details page so the decision maker can inspect the request. Oracle creation guide

Choose participants deliberately. Potential owners can claim work; an actual owner handles the assigned task. Business administrators have separate management responsibilities. Resolve the appropriate manager from application rules rather than embedding a person's username throughout your pages. APEX supports dynamic user participants and authorization schemes. Task Definition concepts

Create one task for one request

The declarative route is a Human Task - Create page process. Select the definition, map the Details Primary Key Item to the saved request ID, and capture the returned task ID in a page item. Sequence it after successful validation and saving of the request. Page-process configuration

For a PL/SQL integration, this illustrates the equivalent API call within an authenticated APEX page process. It assumes the definition, participants, and page items already exist, with no required task parameters:

begin
    :P10_TASK_ID := apex_human_task.create_task(
        p_task_def_static_id     => 'LEAVE_APPROVAL',
        p_subject                => 'Leave request ' || :P10_REQUEST_ID,
        p_initiator              => :APP_USER,
        p_initiator_can_complete => false,
        p_detail_pk              => :P10_REQUEST_ID
    );
end;

The function returns the task ID. Initial assignment depends on the potential owners: one owner gives an Assigned task; several give an Unassigned task that can be claimed. No potential owner raises an error. CREATE_TASK API

Keep the business outcome consistent

Retain the link between the business request and task ID. Before creating a task, check on the server that the user may submit that request and that another submission has not already created its task. Make duplicate prevention part of the transaction design.

Explicitly implement the approval outcome in your business layer: completing a task alone does not define every update your leave system needs. Configure notifications and exception handling, and test with distinct requester, manager, and unrelated-user accounts. Cover rejection, duplicate submission, missing approvers, and failed business updates. Keep task state and business-request status separate in your design and reconcile failures visibly.

النسخة العربية

استخدمت في البوست الأصلي على LinkedIn مثال طلب الإجازة لشرح مهام الموافقات في Oracle APEX. البداية المفيدة هي الفصل بين ثلاث حاجات: سجل الطلب، والقرار البشري، والعملية التي تربط عدة خطوات معًا.

تصف Task Definition مهمة بشرية قابلة لإعادة الاستخدام. ويمكن لكل طلب يتم تقديمه إنشاء نسخة مستقلة من المهمة. أما Workflow أوسع فيقدر ينسّق أنشطة إضافية؛ والموافقة الواحدة لا تستلزم تصميم Workflow كامل من البداية.

حدّد القرار والمشاركين فيه

من Shared Components، افتح Task Definitions تحت Workflows and Automations. في مثال للتطوير، أنشئ Approval Task بمعرّف ثابت LEAVE_APPROVAL. أما Action Task فتناسب العمل المطلوب إتمامه بدون نتيجة موافقة أو رفض. جهّز صفحة تفاصيل المهمة حتى يستطيع صاحب القرار مراجعة الطلب. دليل Oracle للإنشاء

اختَر المشاركين بعناية. يستطيع Potential Owners استلام العمل المتاح، ويتعامل Actual Owner مع المهمة المسندة إليه. ولـBusiness Administrators مسؤوليات إدارية مستقلة. حدّد المدير المناسب من قواعد التطبيق بدل تكرار اسم مستخدم معين داخل الصفحات. تدعم APEX تحديد المشاركين ديناميكيًا واستخدام Authorization Schemes. مفاهيم Task Definition

أنشئ مهمة واحدة لكل طلب

المسار التصريحي هو Page Process من نوع Human Task - Create. اختَر التعريف، واربط Details Primary Key Item بمعرّف الطلب المحفوظ، واحفظ معرّف المهمة الناتج في Page Item. رتّب العملية بعد نجاح التحقق وحفظ الطلب. إعداد عملية الصفحة

وعند التكامل باستخدام PL/SQL، يوضّح المثال التالي استدعاء الـAPI المكافئ داخل عملية صفحة APEX لمستخدم مسجّل دخوله. يفترض وجود التعريف والمشاركين وعناصر الصفحة، وعدم وجود Task Parameters إلزامية:

begin
    :P10_TASK_ID := apex_human_task.create_task(
        p_task_def_static_id     => 'LEAVE_APPROVAL',
        p_subject                => 'Leave request ' || :P10_REQUEST_ID,
        p_initiator              => :APP_USER,
        p_initiator_can_complete => false,
        p_detail_pk              => :P10_REQUEST_ID
    );
end;

ترجع الدالة معرّف المهمة. ويتوقف الإسناد الأولي على Potential Owners: وجود شخص واحد ينشئ مهمة Assigned، ووجود أكثر من شخص ينشئ مهمة Unassigned يمكن استلامها. وعدم وجود مسؤول محتمل يسبب خطأ. توثيق CREATE_TASK

حافظ على اتساق نتيجة العمل

احتفظ بالربط بين طلب العمل ومعرّف المهمة. قبل إنشاء المهمة، تحقّق على السيرفر من صلاحية المستخدم لتقديم الطلب ومن عدم إنشاء مهمة له بالفعل بسبب تقديم سابق. اجعل منع التكرار جزءًا من تصميم المعاملة.

نفّذ أثر الموافقة صراحةً في طبقة قواعد العمل: إتمام المهمة وحده لا يحدد كل تحديث يحتاجه نظام الإجازات. اضبط التنبيهات ومعالجة الاستثناءات، واختبر بحسابات منفصلة لمقدّم الطلب والمدير ومستخدم غير مختص. اختبر الرفض، وتكرار التقديم، وغياب المسؤولين، وفشل تحديث بيانات العمل. افصل بين حالة المهمة وحالة طلب العمل في التصميم، واجعل معالجة حالات الفشل واضحة للمستخدم المختص.
