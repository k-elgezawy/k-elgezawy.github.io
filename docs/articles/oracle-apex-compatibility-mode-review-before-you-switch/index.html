وضع التوافق في Oracle APEX: راجع قبل التغيير

English version

Changing Compatibility Mode in Oracle APEX deserves a review, even when the application already runs on a newer APEX installation. My original LinkedIn post focused on that decision: prepare a recoverable copy, inspect the application, and test the user journeys before changing runtime behavior.

Understand what you are changing

Compatibility Mode controls selected runtime behavior for an application. It is separate from the installed APEX release, the Universal Theme version, and the application’s own version label. Oracle documents mode changes by release; newer modes include earlier compatibility changes. Review the release-specific behavior notes rather than assuming that every JavaScript or visual difference is caused by this setting.

Build a review sequence

  1. Capture a baseline. Keep an application export or source revision and record the existing mode. Preserve related deployment information needed to reproduce the application. An application export is not a backup of all business data or external services.
  2. Use a development copy. Establish how the important journeys behave before changing anything. A list of page numbers is less useful than a list of tasks users must complete.
  3. Inspect the available upgrades. In Utilities → Upgrade Application, review the offered component changes individually. Treat the wizard as a targeted migration tool, not proof that every customization is compatible.
  4. Review theme and custom code separately. Check the Universal Theme and application JavaScript against the target release. Keep these changes distinguishable so a regression can be traced to its cause.
  5. Change the mode deliberately. In Application Definition → Definition → Properties, select the reviewed Compatibility Mode. Repeat the same journeys and compare the results with the baseline.

Oracle’s application upgrade guide explains the component-upgrade and compatibility-setting paths. The practical goal is evidence that the application still works, not simply a newer setting value.

Test outcomes, not only page rendering

For example, take one request from creation through validation, save, review, and approval. Check required fields, LOV selections, Dynamic Actions, dialogs, report filters, downloads, and access rules relevant to that journey. Include cancellation and rejected input. Record expected and observed outcomes, with enough detail to investigate a difference.

These are proposed checks, not claims that every listed component changes with each compatibility mode.

Update the checking tools too

My earlier post recommended Advisor. There is an important release-specific update: APEX Advisor is deprecated in APEX 26.2. Oracle points to enhanced APEXlang quality and security checks in SQLcl 26.3.0 CODESCAN. See the official deprecation notice. Use tools supported by your installed release, and keep functional testing alongside static checks.

A useful change record answers four questions: what changed, why it changed, what was tested, and how the previous application definition can be recovered if necessary.

النسخة العربية

تغيير Compatibility Mode في Oracle APEX يستحق مراجعة، حتى لو التطبيق يعمل بالفعل على تثبيت أحدث من APEX. البوست الأصلي على LinkedIn كان عن القرار ده: احتفظ بنسخة يمكن الرجوع لها، وراجع التطبيق، واختبر رحلات المستخدم قبل تغيير سلوك التشغيل.

افهم ما الذي تغيّره

Compatibility Mode يتحكم في سلوكيات محددة أثناء تشغيل التطبيق. وهو مختلف عن إصدار APEX المثبت، وإصدار Universal Theme، ورقم النسخة الذي تكتبه لتطبيقك. توثّق Oracle تغييرات التوافق لكل إصدار، وتشمل الأوضاع الأحدث تغييرات التوافق السابقة. راجع ملاحظات السلوك الخاصة بالإصدار، بدل افتراض أن أي اختلاف في JavaScript أو الشكل سببه الإعداد ده.

جهّز تسلسلًا للمراجعة

  1. احتفظ بخط أساس. احفظ Export للتطبيق أو نسخة من المصدر، وسجّل وضع التوافق الحالي. احتفظ كذلك بمعلومات النشر اللازمة لإعادة إنشاء التطبيق. تصدير التطبيق ليس نسخة احتياطية لكل بيانات العمل أو الخدمات الخارجية.
  2. استخدم نسخة تطوير. حدّد كيف تعمل الرحلات المهمة قبل أي تغيير. قائمة بالمهام التي يجب أن يكملها المستخدم أفيد من مجرد قائمة بأرقام الصفحات.
  3. راجع الترقيات المتاحة. من Utilities → Upgrade Application، افحص تحديثات المكونات المعروضة كلًّا على حدة. المعالج أداة لترحيل تغييرات محددة، وليس دليلًا على توافق كل التخصيصات.
  4. راجع الثيم والكود المخصص بصورة مستقلة. قارن Universal Theme وJavaScript الخاص بالتطبيق بمتطلبات الإصدار المستهدف. حافظ على إمكانية التمييز بين التغييرات حتى يسهل معرفة سبب أي خلل.
  5. غيّر الوضع بقرار واضح. من Application Definition → Definition → Properties، اختر Compatibility Mode الذي راجعته. أعد تنفيذ الرحلات نفسها وقارن نتائجها بخط الأساس.

يوضح دليل Oracle لترقية التطبيقات مسارات ترقية المكونات وإعداد التوافق. الهدف العملي هو وجود دليل أن التطبيق ما زال يعمل، وليس مجرد اختيار قيمة أحدث.

اختبر النتائج، وليس فتح الصفحة فقط

مثلًا، تابع طلبًا من إنشائه إلى التحقق من البيانات والحفظ والمراجعة والاعتماد. راجع الحقول المطلوبة واختيارات LOVs وDynamic Actions والنوافذ والتصفية وتنزيل الملفات والصلاحيات المرتبطة بالرحلة. أضف الإلغاء والمدخلات المرفوضة للاختبار. دوّن النتيجة المتوقعة والفعلية بتفاصيل تكفي لتشخيص الاختلاف.

دي اختبارات مقترحة، وليست ادعاءً بأن كل المكونات المذكورة يتغير سلوكها مع كل وضع توافق.

حدّث أدوات الفحص أيضًا

البوست السابق أوصى بـAdvisor. هنا تحديث مهم مرتبط بالإصدار: أداة APEX Advisor أصبحت Deprecated في APEX 26.2. وتشير Oracle إلى فحوصات جودة وأمان محسّنة لتطبيقات APEXlang داخل CODESCAN في SQLcl 26.3.0. راجع إشعار الإهمال الرسمي. استخدم الأدوات التي يدعمها إصدارك، واحتفظ بالاختبارات الوظيفية بجانب الفحص الساكن.

سجل التغيير المفيد يجيب عن أربعة أسئلة: ما الذي تغيّر؟ ولماذا؟ وما الذي اختُبر؟ وكيف يمكن استعادة تعريف التطبيق السابق عند الحاجة؟
