تناولت في بوست سابق على LinkedIn دالة تسجيل دخول مخصصة في Oracle APEX. قبل تنفيذ مقارنة كلمة المرور، فيه قرار تصميمي آخر يستحق المراجعة: إيه بالضبط اللي بيحدد هوية الحساب؟

لو `Alice` و`ALICE` و` Alice ` بيوصلوا لنفس الحساب في جزء من النظام، ولحسابات مختلفة في جزء آخر، ممكن يبقى عندك تحقق صحيح من كلمة المرور فوق نموذج هوية غير متسق. المثال التالي يستخدم بيانات افتراضية لكشف المشكلة قبل تغيير مسار تسجيل الدخول.

## افصل مسار الدخول عن التحقق من بيانات الاعتماد

Authentication Scheme بتحدد الهوية، وبعدها APEX تتيح هوية المستخدم المسجّل دخوله من خلال `APP_USER`. فضّل Scheme جاهزة متاحة عندما تناسب مزوّد الهوية ومتطلبات التشغيل. اختيار Custom Authentication معناه تحمّل مسؤولية التكامل ومسارات الفشل، مش مجرد كتابة دالة ترجع Boolean. [Oracle: مفاهيم تسجيل الدخول](https://docs.oracle.com/en/database/oracle/apex/26.2/htmdb/understanding-authentication.html)

في Scheme تستخدم اسم المستخدم وكلمة المرور، تستدعي `APEX_AUTHENTICATION.LOGIN` التحقق من بيانات الاعتماد، ثم تدير معالجة ما بعد نجاح الدخول والتسجيل وإعادة التوجيه. القيمة الافتراضية للمعامل `p_uppercase_username` هي `TRUE`. التفصيلة دي مهمة لو مستودع الحسابات بيفرّق بين الحروف الكبيرة والصغيرة. [Oracle: توثيق LOGIN](https://docs.oracle.com/en/database/oracle/apex/26.2/aeapi/LOGIN-Procedure.html)

## اختبر قواعد توحيد الأسماء ببيانات مؤقتة

افترض إن السياسة المقترحة لا تفرّق بين حالة الحروف في اسم المستخدم وتتجاهل المسافات المحيطة. الاستعلام التالي يوضح التعارضات الناتجة، بدون إنشاء جدول أو تعديل بيانات:

```sql
with demo_users (user_id, login_name) as (
    select 101, 'Alice' from dual union all
    select 102, 'ALICE' from dual union all
    select 103, ' bob ' from dual union all
    select 104, 'BOB'   from dual union all
    select 105, 'Carla' from dual
)
select upper(trim(login_name)) as login_key,
       count(*) as matching_accounts
from demo_users
group by upper(trim(login_name))
having count(*) > 1
order by login_key;
```

الصفوف المتوقعة لهذه الأمثلة بحروف ASCII:

```text
LOGIN_KEY  MATCHING_ACCOUNTS
ALICE      2
BOB        2
```

النتيجة بتقول إن فيه سجلّين مختلفين بيتنافسوا على كل مفتاح مقترح. احسم ملكية الحسابات وسياسة الانتقال قبل فرض عدم التكرار. ما تختارش أول سجل مطابق بشكل عشوائي.

ده اختبار لفكرة تصميم، مش قاعدة عامة لكل أسماء المستخدمين. في نظام متعدد الجهات، ممكن تحتاج مفتاحًا مركبًا يتضمن الجهة. والأسماء الدولية تحتاج سياسة صريحة لـUnicode وقواعد المقارنة وتوحيد النصوص؛ مثال ASCII ده ما بيحسمش القواعد دي. طبّق السياسة المختارة باتساق أثناء إنشاء الحساب والبحث عنه واستعادته وربط الحسابات.

## حدّد التعامل مع حالة الحروف صراحةً

لو سياسة الهوية التي راجعتها تقصد الحفاظ على حالة الحروف، ممكن لعملية صفحة تسجيل الدخول التي تحتوي بالفعل على عناصر الاسم وكلمة المرور استخدام المثال التالي:

```sql
begin
    apex_authentication.login(
        p_username           => :P9999_USERNAME,
        p_password           => :P9999_PASSWORD,
        p_uppercase_username => false
    );
end;
```

عدّل أسماء العناصر وراجع Authentication Scheme الفعّالة قبل الاستخدام. مكان الاستدعاء هو عملية تسجيل الدخول؛ ودالة التحقق في الـScheme تقدم قرار صحة بيانات الاعتماد. تغيير المعامل وحده لا ينقل مفاتيح الحسابات القديمة ولا يصلح استعلام بحث يستخدم قواعد متعارضة. ولا تحوّل كلمة المرور لحروف كبيرة أو تحذف مسافاتها لمجرد تطبيق نفس قاعدة اسم المستخدم.

## ضع عقدًا مستقلًا لتخزين كلمات المرور

استخدام SHA-512 مرة واحدة، حتى مع دمج بعض بيانات الحساب، لا يساوي تصميمًا حديثًا لتخزين كلمات المرور بخوارزمية قابلة لضبط كلفة الحساب. استخدم مكوّن تحقق مدعومًا يطبق خوارزمية مناسبة مثل Argon2id، مع Salt مستقل لكل كلمة مرور ومعاملات كلفة تمت مراجعتها. احتفظ ببيانات الخوارزمية ومعاملاتها اللازمة للتحقق والترقية. [OWASP: تخزين كلمات المرور](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

حدّد رسالة فشل عامة للمستخدم، وضبطًا لمحاولات الدخول، وسلوك استعادة الحساب، والمصادقة متعددة العوامل المناسبة. احمِ تفاصيل التشخيص ولا تسجّل بيانات الاعتماد في الـLogs. [OWASP: إرشادات تسجيل الدخول](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

قبل الإطلاق، اختبر البيانات الصحيحة، وكلمة المرور الخاطئة، والحساب غير الموجود أو الموقوف، واختلاف حالة الحروف، والمسافات، وتكرار الأسماء بعد توحيدها، وتعطل مكوّن التحقق. راجع قيمة `APP_USER` الناتجة وربطها بالحساب. الأمثلة السابقة بتوضح التصميم والنتائج المتوقعة، ولا تنفّذ خدمة تحقق متكاملة أو تدّعي تحسنًا مقاسًا في الأداء.
